# AGENTS.md

Guidance for AI coding agents working in this repository.

## Read First

- Read [CONTRIBUTING.md](CONTRIBUTING.md) before starting. If you cannot
  follow it, do not start the work.
- gofix is a fork of QuickFIX/Go intended primarily for Appital's internal
  use. Read the "Why a fork?" section of [README.md](README.md) to understand
  what kind of changes fit.
- For anything beyond a small fix, the direction of a change should be agreed
  with the maintainers in an issue before code is written.

## Environment

- Go version: see `go.mod`. The Prometheus metrics implementation is a separate
  module in `metrics/prometheus` with its own `go.mod`.
- Build and test: `make` runs `go vet` and the unit tests (with `-race`) for
  both modules. Use `go test ./<pkg>/...` for a faster loop while iterating.
- Lint: run `golangci-lint run --fix ./...` to fix what can be fixed
  automatically, then make sure `make lint` passes. It lints both modules.
- Format: `make fmt`.
- Fuzzing: `make fuzz` runs each fuzz target for `FUZZ_TIME` (default 1m).
  Their seed corpora run as part of `make test`.
- Acceptance tests: `make generate && make build-test-srv && make accept`
  (needs Ruby on `PATH`).
- Benchmarks: `make bench-baseline`, then `make bench` and `make bench-compare`
  after the change. See [docs/BENCHMARKING.md](docs/BENCHMARKING.md).

## Repository Layout

- Root package `gofix`: the session engine, acceptor, initiator, message
  parsing, building and validation.
- `config/`: setting names and their documentation.
- `datadictionary/`: FIX data dictionary parsing used for validation.
- `store/` and `log/`: message store and log implementations.
- `metrics/prometheus/`: optional Prometheus `MetricsFactory` (separate module).
- `cmd/generate-fix/`: the code generator. `spec/` holds the FIX XML specs it
  reads.
- `gen/`: generated FIX message packages. These are **not checked in**. Never
  edit or commit them; change the generator instead and run `make generate`.
- `internal/`: internal helpers, including the benchmark tape in
  `internal/tape`.
- `_test/`: the QuickFIX acceptance suite and load generator.
- `docs/`: longer-form documentation.

## Code Conventions

- Match the style, naming, comment density and idioms of the surrounding code.
- New files start at the `package` line. Do not add the quickfixengine.org
  copyright header to new files. Leave it in place on existing files.
- Performance matters on the hot path (parsing, validation, message building,
  the session read/write loops). Avoid new per-message allocations there, and
  back any performance claim with benchmark results.
- Keep changes focused. Do not reformat or refactor unrelated code.

## Tests and Documentation

- All code changes need tests. Bug fixes should include a test that fails
  without the fix.
- Changes to the public API (exported Go types and functions, settings in
  `config/`) need Go doc comments and, where relevant, README or `docs/`
  updates.
- User-visible changes need a [CHANGELOG.md](CHANGELOG.md) entry. Breaking
  changes go under `BREAKING CHANGES`.

## Commits and Pull Requests

- Commit subjects and pull request titles use
  [Scoped Commits](https://scopedcommits.com/): `<scope>: <description>`, for
  example `session: Stop allocating on resend requests` or
  `all: Update dependencies`. Do not use Conventional Commits types such as
  `feat:` or `fix:`.
- Pull request descriptions should explain why the change is needed and be no
  longer than necessary. An agent may help draft one, but the human submitting
  the pull request must review it and take responsibility for it.
- Disclose in the pull request that AI tools were used to produce the change.

## Acting on the User's Behalf

- Do not post comments on issues or pull requests, and do not open pull
  requests, unless the user explicitly asks you to in that session. Discussion
  on this repository is for humans.
- Do not push to `main`. All changes go through a reviewed pull request.

## Security

- Use `govulncheck ./...` to check whether a reported dependency vulnerability
  actually affects gofix. If `govulncheck` does not flag it, it is not urgent.
- Never put details of a suspected vulnerability in a public issue, pull
  request or commit message. Follow [SECURITY.md](SECURITY.md).
- Do not commit secrets, real credentials or real counterparty identifiers.
  The keys in `_test_data/` are self-signed test material generated by
  `_test_data/gen-certs.sh`.
